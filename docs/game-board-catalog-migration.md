# GameBoardの分割取得に向けた依存調査

前段のPR #213で既存動作を守るテストと依存調査を追加した。
判定用メタデータ・詳細取得・表示用Hookを用意し、現在は読込入口を保護する段階で、GameBoardの取得先、ゲームルール、
保存形式、P2P通信形式は変更しない。DeckBuilderの分割取得はPR #212で接続済み。

## 現在の取得と利用箇所

`useGameBoardCatalogResources` と `useGameBoardSavedDeckPicker` が
`loadCardCatalog` を呼ぶ。従来の発売済み・先行公開JSONの取得はこのローダーで共有される。
Hookが2つあること自体を二重ダウンロードと見なさない。

| 利用箇所 | 必要な情報・維持する動作 |
| --- | --- |
| `gameBoardCatalog` → `cardStats`、攻撃UI | 全体のatk/hp、数値の解釈、フォロワー判定。欠けると攻撃可否も変わり得る |
| `cardDetails`、Inspector、Zone | 能力文・画像・両面の各項目。裏面の表示値と表面の基礎能力値を混同しない |
| `evolveAutoAttach` | ID、名前、タイトル、種別、デッキ区分、関連参照。デッキ外の再録も同一ファミリーの判定に関与する |
| `fieldLinkAutoAttach`、`fieldLinkRules` | ソースと関連先のルールグループ。同じグループの別IDも必要 |
| `useGameBoardFieldActions` | カタログによる手動リンク対象判定、リンクカード集合、装備・トレジャートークン集合 |
| `gameBoardSavedDecks` | 保存した全セクションのID、構築ルール、コピー数制限、関連トークンの自動補完、完全なカードデータ |
| `useGameBoardSetupActions`、`gameBoardDeckActions` | JSONから盤面カード・トークン候補を作成。現在はカタログ取得を待たない独立した入口 |
| `useGameBoardLogic`、受信処理、保存セッション復元 | 対戦開始以外にもカードが入る。既存の盤面・受信イベントを失わない設計が必要 |
| `snapshot/gameBoardSnapshot` | カタログから復元できる標準画像を送信時に省略する。受信側の画像取得も移行の対象 |

## 部分取得で変わり得る判定

### 進化の再録ファミリー

自身に関連参照のない進化カードでも、同名・同タイトル・同種別・同区分の別版に
参照があれば再録候補を求める。逆に、別版の参照先が矛盾するとファミリーの推測を止める。
直接参照したIDと盤面にいるIDだけでは、候補の欠落だけでなく誤った追加も起こり得る。
`loadCardsWithRelated` の直接・再帰的な参照取得だけで、このファミリー全体は保証されない。

### リンクのグループ

場のカードが「にんじん」を参照している場合、同じグループの「開催大成功！」も
リンク候補になり得る。盤面とソースのIDだけを残すと参照先のグループが分からなくなる。

### 保存デッキの復元

保存セクションにない関連トークンも補完する。カード一覧だけを使ってデッキを復元すると、
枚数が合っていても能力文・両面情報が欠けたデータを返し得る。
また、未取得のIDを本当に存在しないIDと扱うと、合法な保存デッキを一覧から除外してしまう。

## 判定用メタデータの分離

`buildGameBoardCatalogMetadata` は能力値・進化候補・リンク候補・リンクカード集合・
手動リンク対象トークン集合のみを構築する。`GameBoardCatalogRuleCard` は必要な項目に
限定した読み取り専用型で、凍結済みの生成一覧をコピーや完全なカード型への変換なしで渡せる。
能力文・両面・完全なカードの参照表はこの処理から返さない。

既存の `buildGameBoardCatalogResources` はこの判定用処理を利用した上で、
従来どおり完全なデータから `catalogById` と `detailLookup` を作る。
Hook・画面は引き続きこの既存の構築処理を呼び、従来JSONを取得する。
この整理だけでは、実際の取得量はまだ減らない。

- `gameBoardCatalog.test.ts` は再録ファミリー・参照矛盾・別IDのリンクグループの
  同じ期待値を既存処理と新しい判定用処理の双方で検証する。
  凍結済み一覧への対応と、能力文・両面を持つ完全な詳細を生成しないことも確認する。
- `generatedCardCatalogParity.test.ts` は実データ全件の能力値・分類集合・ソース利用可否を比較する。
  全ての利用可能な進化ソースについて、同名カードとその関連先のメインカードを場の候補にして
  従来との一致を比較する。リンクは全メインカードを候補にして比較する。
  これは全ての盤面状態の網羅ではなく、場の所有者や既存アタッチなどの条件は既存の専用テストで守る。

## 独立した詳細取得処理

`createGameBoardCatalogDetails(source)` は、既に開いた1バージョンの取得処理を受け取り、
`load(ids, { includeRelated: true })` で必要な完全な詳細を取得する。
この処理も画面には未接続であり、既存のGameBoardは引き続き従来JSONを読む。

- 作成時には詳細を取得しない。既知IDだけを必要時に要求し、既定では順序と重複を維持する。
  `includeRelated: true` の場合だけ、既存の取得処理を使って関連参照を再帰的に含める。
- 結果は `version`、元の `requestedIds`、一覧にない `unknownIds`、検証済みの `cards`、
  完全な詳細から作った `detailLookup`。一覧を詳細へ変換しない。
  不明IDだけなら通信せず空の詳細と不明IDを返す。
- `unknownIds` はその版の一覧にないIDであり、HTTPの404や詳細の欠損・破損とは区別する。
  既知IDの取得が1つでも失敗すれば呼び出し全体をrejectし、不完全な成功結果を返さない。
  外部カードの情報を保持するか、不明IDを拒否するかは将来の入口ごとの判断とし、
  この処理でカスタムカードや既存の盤面を削除しない。
- 呼び出し元のID配列を同期的にコピーする。各呼び出しは独立し、後の取得が先に終わっても
  先の結果を自動破棄しない。操作の順序・適用可否は将来の呼び出し元で管理する。
- 詳細表示用の参照表は毎回新しく作り、表示用の変更が他の呼び出しへ伝わらない。
  元の検証済みカードは読み取り専用のままで、変換・書き換えを行わない。
- グループ取得の共有・整合性検証・失敗グループのキャッシュ破棄は既存の版固定取得処理が担当する。
  二重のキャッシュや自動再試行を追加せず、同じ版の再呼び出しで再試行する。
  新版・従来JSONへの自動フォールバックは行わない。

主なテスト所有先は `src/utils/gameBoard/gameBoardCatalogDetails.test.ts`。
同時取得、失敗後の再試行、バージョン分離、不明ID、完全な能力文・両面、関連循環を検証する。
`generatedCardCatalogParity.test.ts` は実際の生成物と取得処理を使い、複数グループの一方が404に
なった後の再試行、正常グループのキャッシュ再利用、完全な詳細の保持を検証する。

## 表示用の取得状態管理（画面は未接続）

`useGameBoardGeneratedCardDetails(catalog, ids)` は、版固定の取得処理と現在必要なIDを受け取り、
`idle / loading / ready / error`、`knownCards`、`detailLookup`、`version`、`retry` を返す。
`ready` の `requestedIds` と `unknownIds` は現在の要求に対応し、`knownCards` と参照表は
同じカタログで過去に取得が完了した表示用データも保持する。

- 新しい要求の取得待ち・失敗では、既に検証した表示用データを消さない。
  複数要求が逆順で成功しても双方の詳細を保持し、一覧の順序に揃える。
- 選択が変わった後の同じ版の成功も再利用するが、古い失敗で現在の要求をエラーにしない。
  A→B→Aで最初のAが完了しても、最後のAの要求を完了した扱いにはしない。
- カタログのインスタンス変更・解除では、以前の詳細を即座に公開対象から外す。
  バージョン文字列が同じでもインスタンスごとに分離する。
  アンマウント、以前のカタログ、Strict Modeの破棄された実行の応答も反映しない。
- `retry` は現在のIDを同じ版で再取得するだけで、manifestを開き直さない。
  IDが空なら取得せず `idle` とし、同じ版の表示用データは再利用できるまま保持する。
- このHookは表示用の読み取り専用データを扱う。インポート・盤面変更の操作キューではなく、
  イベントやスナップショットを適用・待機・破棄する処理も持たない。

所有テストは `src/hooks/gameBoard/useGameBoardGeneratedCardDetails.test.ts`。
下位の版固定・完全な詳細の検証は引き続き `gameBoardCatalogDetails.test.ts` と実データ互換性テストが担当する。
GameBoardの既存Hookへの接続はまだ行わない。

## 画面接続時の入口ごとの方針

| 入口 | 次の接続で守る契約 |
| --- | --- |
| 通常のローカル操作・相手のイベント・スナップショット | 既存の適用順とactorを維持し、表示用詳細の通信待ちをネットワーク処理やReducerへ挟まない。適用後のカードID・両プレイヤーのトークン候補から表示用データを取得する |
| 保存対戦の復元 | 盤面復元を詳細取得失敗で消さず、表示用取得を別に進める。対戦中の強制再読み込みはしない |
| JSON読込 | 現在の完全な入力・カスタム画像・外部IDの扱いを維持する。取得したカタログで入力カードを一律に置き換えない |
| 保存デッキの読込 | 表示用一覧の情報をそのまま対戦用に渡さない。全セクションと関連トークンの完全な詳細を取得後、保存レコードと対象プレイヤーのimport可否を再確認してから一括反映する。閉じる・リセット・対象変更後の古い結果は適用しない |
| 汎用トークン・未知のID | 一覧にないIDを通信失敗と見なさず、既存のカードやトークン候補を削除しない |

この表は分割カタログへの接続条件であり、分割データを使うイベント・インポート処理はまだ未接続である。
画像だけが省略された受信カードには一覧の画像も使えるが、一覧から空の能力文・両面情報を作らない。
詳細待ち・失敗・不明IDのInspector表示、および旧版削除時の対戦を保つ復旧手順は、
画面接続前に個別のテストと実装が必要。

## JSONファイル読込入口の競合防止

分割取得を接続する前に、既存の `useGameBoardSetupActions` のFileReader完了処理を保護する。
読込開始時だけの判定では、遅い読込がローカルリセット後や別のデッキ読込後に盤面を上書きし得る。

- ファイル読込ごとにプレイヤー別の識別子と、そのプレイヤーのカード・トークン構成を記録する。
  同じプレイヤーの新しい読込や同期的なデッキ読込で以前の要求を無効にする。
  相手側の読込・revision更新で自分の読込を取り消さない。
- ローカルのリセット確定、操作権限の喪失、role変更、アンマウントで要求を無効にする。
  権限やroleが元に戻っても、以前の要求を復活させない。
- 完了時は最新の操作権限・準備条件・本人の構成を再確認する。
  GameBoardから既存の `gameStateRef` を渡し、Reactの再描画前でも現在の状態を参照する。
  条件に合わない要求はJSON解析前に捨てるため、古い不正JSONの警告も出さない。
- 画像と表示名だけの差は構成変更と見なさない。標準画像を省略したネットワークスナップショットで
  有効な読込を取り消さず、大きなカスタム画像を比較用JSONへ複製しない。
- 有効なJSONの分類・シャッフル・送信イベント形式と、現行のJSON解析失敗の警告は維持する。
  これはファイル読込入口の保護であり、ネットワーク全体のセッション管理や
  将来の保存デッキ詳細取得のガードを代行しない。

所有テストは `src/hooks/gameBoard/useGameBoardSetupActions.test.tsx`。
`e2e/solo-import-race.spec.ts` ではネイティブFileReaderの開始を遅らせ、
リセット後の反映防止と、新旧の読込が逆順に完了した場合を実ブラウザーで検証する。

## 次の実装を始める条件と順序

1. 【構築処理は分離済み、画面接続は未実施】一覧から作れる判定用メタデータと、完全な詳細が必要な処理を区別する。
   一覧には名前・種別・関連参照・能力値があるが、能力文・両面はない。
   一覧を既存の詳細ビルダーへ渡して空の能力文を成功結果と扱わない。
2. 【比較テスト追加済み】一覧全体による進化ファミリー・リンク判定が従来と一致することを、
   今回の合成例と実データで検証する。選択したデッキだけを基準にファミリーを再構築しない。
3. 【独立処理とテスト追加済み、画面は未接続】ID単位の詳細取得・版固定・失敗時の再試行を独立した処理で実装する。
   GameBoardのためにDeckBuilderのページ選択Hookや操作キャンセル方針をそのまま流用しない。
4. 【JSONファイル読込の競合防止は実装済み、分割データの操作への接続は未実施】保存デッキ、JSON読込、保存対戦の復元、相手からのイベント・スナップショット、
   トークン生成の各入口について、取得待ち中の順序と対象プレイヤーを守る方式を決める。
   保存デッキ一覧の検証用データを、そのまま対戦用データとして渡さない。
5. 対戦中の取得失敗で盤面や受信内容を消さず、未取得詳細を再試行できる設計にする。
   DeckBuilderと同様の再読み込み案内だけでは、進行中の対戦保護の代わりにならない。
   旧版削除時の再接続・復元も含めて設計してから接続する。
6. 画面接続は別PRにし、単体・Hook・通常/本番E2E・Vercel確認で検証する。
   データ待ちで相手との同期が崩れないことを確認し、初回とデッキ読込後の取得量を測る。

追加の外部ストレージ・有料サービス・生成バイナリのGit管理は導入しない。
従来JSONの公開停止や削除は、全利用箇所の移行と配信確認が終わるまで別工程とする。
