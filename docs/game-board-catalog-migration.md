# GameBoardの分割取得に向けた依存調査

前段のPR #213で既存動作を守るテストと依存調査を追加した。
判定用メタデータ・詳細取得・表示用Hookを用意し、読込入口の保護を経て、現在はGameBoardの分割取得を画面へ接続した。ゲームルールは維持する。
同期・保存状態には、後述の省略可能なリセット目印を追加する。DeckBuilderの分割取得はPR #212で接続済み。

## 現在の画面接続

GameBoardは `useGameBoardActiveCatalogResources` から生成カタログを利用する。
以下の各段階の記述は移行前の依存調査と実装経緯であり、「未接続」はその段階時点の状態を示す。

- 空の盤面ではmanifestとindexだけを取得する。ルール用メタデータはデッキ外も含む一覧全体から構築する。
- 盤面・両プレイヤーのトークン候補・一時的なLook TopのIDを重複除去・ソートし、その集合の詳細だけを取得する。
  移動・カウンター・並び替えだけでは再要求しない。未知のIDは削除せず、通信失敗と区別する。
- 省略された画像は一覧から表示用カードへだけ補う。同期状態・保存・カスタム画像は書き換えない。
  能力文や両面は完全な詳細のみから表示し、一覧を完全な詳細に変換しない。
- 保存デッキ一覧は同じ版のReaderのsummariesを使い、選択後に完全な詳細と関連カードを取得する。
  既存のレコード再確認・閉じる・リセット・対象変更の完了ガードを維持する。
  空の盤面で保存デッキの詳細取得が失敗した場合も、ダイアログからカタログを読み直せる。
  読み直しだけでは自動インポートせず、再度Loadを明示操作する。
- Inspectorのカード別状態・同版再試行・明示的な新版への復旧を画面へ接続した。
  新版の検証が失敗した場合は旧版を保持し、自動リロードしない。
- HTTP待ちをReducer・イベント・スナップショット受信へ挟まない。読み取り用refはコミット時に更新し、
  アンマウントで解除する。通信のメッセージや保存形式・ゲームルールは変更しない。

主な所有テストは `useGameBoardActiveCatalogResources.test.ts`（対象ID・全体メタデータ・画像補完・ref）、
`GameBoard.test.tsx`（Inspector配線）、`GameBoardDialogUi.test.tsx`（保存デッキ復旧の親部品経由の配線）、
`useGameBoardLogic.test.tsx`（取得待ち/失敗中の操作と受信）。
保存デッキ・版固定・復旧の契約は既存の専用Hook/utilityテストが引き続き担う。
ブラウザーでは `card-catalog-loading.spec.ts`、`game-board-catalog-retry.spec.ts`、
`game-board-generated-recovery.spec.ts`、本番用 `production/game-board-catalog.spec.ts` が接続を検証する。

### 未使用の旧HTTP取得処理の整理

分割取得への画面接続後、実行時の参照がなくなった `loadCardCatalog` と
`useGameBoardCatalogResources` を削除した。読込状態の型は
`gameBoardCatalogTypes.ts` に移し、表示部品から旧Hookへの型依存も解消した。
`mergeCardCatalogs` と `buildGameBoardCatalogResources` は実データ互換性比較の純関数として維持する。

旧HTTP取得専用8件と旧Hook専用6件のテストは対象APIの廃止に合わせて削除した。
現行の安全網は次のテストが引き続き担当する。現行テストの期待値や待機時間は緩和しない。

| 契約 | 現行の所有テスト |
| --- | --- |
| 並列取得の共有・検証済みキャッシュ・各失敗からの再試行 | `generatedCardCatalog.test.ts` |
| 初回読込失敗・明示的な復旧・版の保持 | `useGameBoardGeneratedCatalogResources.test.ts` |

これは未使用コードの整理であり、初回転送量の追加削減を伴わない。

これまでに開いた旧アプリが使うURLの配信変更と、indexそのものの縮小は別工程とする。

### 取得量の比較

7,684件の現データと生成物を対象に、従来JSON2本とmanifest/index/必要グループのファイルサイズを比較した。
以下は圧縮率比較用のgzipサイズであり、Vercelの実際のContent-Encodingやブラウザーキャッシュを含む実測転送量ではない。

| 状態 | 非圧縮bytes | gzip bytes |
| --- | ---: | ---: |
| 従来JSON全体 | 7,286,646 | 510,969 |
| 新方式の空の盤面（manifest + index） | 4,620,702 | 275,719 |
| 構築済みロイヤルサンプルの完全な詳細と関連参照を追加後 | 5,552,883 | 355,261 |

初回のgzip比較は約46%減、サンプルの詳細追加後は約30%減。
サンプルの対象グループはBP16/BP17/BP18/CP04/EBD03/EBD04/PCS01の7つ。
グループ単位の取得であり、別のデッキや対象ID数によって効果は変わる。index全体の増加は残る。
開発Strict Modeでは初回openが2回実行される。本番用E2Eはmanifest/index各1回、詳細と従来JSONは0回を検証する。

### indexの圧縮表現への移行

schema 2では一覧の項目名を共通ヘッダーにまとめ、値と項目の有無を行ごとに記録する。
アプリへ渡す一覧は従来と同じオブジェクトへ復元するため、全件ルール判定・画像・検索・保存デッキの入力型は維持する。
新しいReaderはschema 1も読める。旧schema 1を保持した状態で詳細404が発生し、schema 2へ明示的に復旧しても
盤面と対戦を保持することを`game-board-generated-recovery.spec.ts`で検証する。
更新前のschema 1専用アプリが新manifestを取得した場合は、ブラウザーでの再読み込みが必要となる。

同じ現データのmanifest/indexは3,000,040 bytes / gzip 239,645 bytesとなる。
前段のオブジェクト一覧との比較ではgzipで約13%減、従来JSON全体との比較では約53%減。
ロイヤルサンプルの詳細追加後は3,932,221 bytes / gzip 319,187 bytes。
いずれもファイルサイズ比較であり、実際の配信圧縮やキャッシュを含む実測転送量ではない。
形式とテストの詳細は`card-catalog-artifacts.md`を参照する。

## 部分取得で変わり得る判定

### 進化の再録ファミリー

自身に関連参照のない進化カードでも、同名・同タイトル・同種別・同区分の別版に
参照があれば再録候補を求める。逆に、別版の参照先が矛盾するとファミリーの推測を止める。
直接参照したIDと盤面にいるIDだけでは、候補の欠落だけでなく誤った追加も起こり得る。
`loadCardsWithRelated` の直接・再帰的な参照取得だけで、このファミリー全体は保証されない。

### リンクのグループ

場のカードが「にんじん」を参照している場合、同じグループの「開催大成功！」も
リンク候補になり得る。盤面とソースのIDだけを残すと参照先のグループが分からなくなる。

### 保存デッキの復元

保存セクションにない関連トークンも補完する。カード一覧だけを使ってデッキを復元すると、
枚数が合っていても能力文・両面情報が欠けたデータを返し得る。
また、未取得のIDを本当に存在しないIDと扱うと、合法な保存デッキを一覧から除外してしまう。

## 判定用メタデータの分離

`buildGameBoardCatalogMetadata` は能力値・進化候補・リンク候補・リンクカード集合・
手動リンク対象トークン集合のみを構築する。`GameBoardCatalogRuleCard` は必要な項目に
限定した読み取り専用型で、凍結済みの生成一覧をコピーや完全なカード型への変換なしで渡せる。
能力文・両面・完全なカードの参照表はこの処理から返さない。

既存の `buildGameBoardCatalogResources` はこの判定用処理を利用した上で、
従来どおり完全なデータから `catalogById` と `detailLookup` を作る。
Hook・画面は引き続きこの既存の構築処理を呼び、従来JSONを取得する。
この整理だけでは、実際の取得量はまだ減らない。

- `gameBoardCatalog.test.ts` は再録ファミリー・参照矛盾・別IDのリンクグループの
  同じ期待値を既存処理と新しい判定用処理の双方で検証する。
  凍結済み一覧への対応と、能力文・両面を持つ完全な詳細を生成しないことも確認する。
- `generatedCardCatalogParity.test.ts` は実データ全件の能力値・分類集合・ソース利用可否を比較する。
  全ての利用可能な進化ソースについて、同名カードとその関連先のメインカードを場の候補にして
  従来との一致を比較する。リンクは全メインカードを候補にして比較する。
  これは全ての盤面状態の網羅ではなく、場の所有者や既存アタッチなどの条件は既存の専用テストで守る。

## 独立した詳細取得処理

`createGameBoardCatalogDetails(source)` は、既に開いた1バージョンの取得処理を受け取り、
`load(ids, { includeRelated: true })` で必要な完全な詳細を取得する。
この処理も画面には未接続であり、既存のGameBoardは引き続き従来JSONを読む。

- 作成時には詳細を取得しない。既知IDだけを必要時に要求し、既定では順序と重複を維持する。
  `includeRelated: true` の場合だけ、既存の取得処理を使って関連参照を再帰的に含める。
- 結果は `version`、元の `requestedIds`、一覧にない `unknownIds`、検証済みの `cards`、
  完全な詳細から作った `detailLookup`。一覧を詳細へ変換しない。
  不明IDだけなら通信せず空の詳細と不明IDを返す。
- `unknownIds` はその版の一覧にないIDであり、HTTPの404や詳細の欠損・破損とは区別する。
  既知IDの取得が1つでも失敗すれば呼び出し全体をrejectし、不完全な成功結果を返さない。
  外部カードの情報を保持するか、不明IDを拒否するかは将来の入口ごとの判断とし、
  この処理でカスタムカードや既存の盤面を削除しない。
- 呼び出し元のID配列を同期的にコピーする。各呼び出しは独立し、後の取得が先に終わっても
  先の結果を自動破棄しない。操作の順序・適用可否は将来の呼び出し元で管理する。
- 詳細表示用の参照表は毎回新しく作り、表示用の変更が他の呼び出しへ伝わらない。
  元の検証済みカードは読み取り専用のままで、変換・書き換えを行わない。
- グループ取得の共有・整合性検証・失敗グループのキャッシュ破棄は既存の版固定取得処理が担当する。
  二重のキャッシュや自動再試行を追加せず、同じ版の再呼び出しで再試行する。
  新版・従来JSONへの自動フォールバックは行わない。

主なテスト所有先は `src/utils/gameBoard/gameBoardCatalogDetails.test.ts`。
同時取得、失敗後の再試行、バージョン分離、不明ID、完全な能力文・両面、関連循環を検証する。
`generatedCardCatalogParity.test.ts` は実際の生成物と取得処理を使い、複数グループの一方が404に
なった後の再試行、正常グループのキャッシュ再利用、完全な詳細の保持を検証する。

## 表示用の取得状態管理（画面は未接続）

`useGameBoardGeneratedCardDetails(catalog, ids)` は、版固定の取得処理と現在必要なIDを受け取り、
`idle / loading / ready / error`、`knownCards`、`detailLookup`、`version`、`retry` を返す。
`ready` の `requestedIds` と `unknownIds` は現在の要求に対応し、`knownCards` と参照表は
同じカタログで過去に取得が完了した表示用データも保持する。

- 新しい要求の取得待ち・失敗では、既に検証した表示用データを消さない。
  複数要求が逆順で成功しても双方の詳細を保持し、一覧の順序に揃える。
- 選択が変わった後の同じ版の成功も再利用するが、古い失敗で現在の要求をエラーにしない。
  A→B→Aで最初のAが完了しても、最後のAの要求を完了した扱いにはしない。
- カタログのインスタンス変更・解除では、以前の詳細を即座に公開対象から外す。
  バージョン文字列が同じでもインスタンスごとに分離する。
  アンマウント、以前のカタログ、Strict Modeの破棄された実行の応答も反映しない。
- `retry` は現在の失敗後だけ、現在のIDを同じ版で再取得する。連打・取得中・成功後・アンマウント後は追加取得せず、manifestを開き直さない。
  IDが空なら取得せず `idle` とし、同じ版の表示用データは再利用できるまま保持する。
- このHookは表示用の読み取り専用データを扱う。インポート・盤面変更の操作キューではなく、
  イベントやスナップショットを適用・待機・破棄する処理も持たない。

所有テストは `src/hooks/gameBoard/useGameBoardGeneratedCardDetails.test.ts`。
下位の版固定・完全な詳細の検証は引き続き `gameBoardCatalogDetails.test.ts` と実データ互換性テストが担当する。
GameBoardの既存Hookへの接続はまだ行わない。

## 画面接続時の入口ごとの方針

| 入口 | 次の接続で守る契約 |
| --- | --- |
| 通常のローカル操作・相手のイベント・スナップショット | 既存の適用順とactorを維持し、表示用詳細の通信待ちをネットワーク処理やReducerへ挟まない。適用後のカードID・両プレイヤーのトークン候補から表示用データを取得する |
| 保存対戦の復元 | 盤面復元を詳細取得失敗で消さず、表示用取得を別に進める。対戦中の強制再読み込みはしない |
| JSON読込 | 現在の完全な入力・カスタム画像・外部IDの扱いを維持する。取得したカタログで入力カードを一律に置き換えない |
| 保存デッキの読込 | 表示用一覧の情報をそのまま対戦用に渡さない。全セクションと関連トークンの完全な詳細を取得後、保存レコードと対象プレイヤーのimport可否を再確認してから一括反映する。閉じる・リセット・対象変更後の古い結果は適用しない |
| 汎用トークン・未知のID | 一覧にないIDを通信失敗と見なさず、既存のカードやトークン候補を削除しない |

この表は分割カタログへの接続条件であり、分割データを使うイベント・インポート処理はまだ未接続である。
画像だけが省略された受信カードには一覧の画像も使えるが、一覧から空の能力文・両面情報を作らない。
詳細待ち・失敗・不明IDのInspector表示と、旧版削除時の対戦を保つ復旧用Hookは下記の独立実装で保護する。
通常ページへの配線は、分割カタログの画面接続時に行う。

## JSONファイル読込入口の競合防止

分割取得を接続する前に、既存の `useGameBoardSetupActions` のFileReader完了処理を保護する。
読込開始時だけの判定では、遅い読込がローカルリセット後や別のデッキ読込後に盤面を上書きし得る。

- ファイル読込ごとにプレイヤー別の識別子と、そのプレイヤーのカード・トークン構成を記録する。
  同じプレイヤーの新しい読込や同期的なデッキ読込で以前の要求を無効にする。
  相手側の読込・revision更新で自分の読込を取り消さない。
- ローカルのリセット確定、操作権限の喪失、role変更、アンマウントで要求を無効にする。
  権限やroleが元に戻っても、以前の要求を復活させない。
- 完了時は最新の操作権限・準備条件・本人の構成を再確認する。
  GameBoardから既存の `gameStateRef` を渡し、Reactの再描画前でも現在の状態を参照する。
  条件に合わない要求はJSON解析前に捨てるため、古い不正JSONの警告も出さない。
- 画像と表示名だけの差は構成変更と見なさない。標準画像を省略したネットワークスナップショットで
  有効な読込を取り消さず、大きなカスタム画像を比較用JSONへ複製しない。
- 有効なJSONの分類・シャッフル・送信イベント形式と、現行のJSON解析失敗の警告は維持する。
  これはファイル読込入口の保護であり、ネットワーク全体のセッション管理や
  将来の保存デッキ詳細取得のガードを代行しない。

所有テストは `src/hooks/gameBoard/useGameBoardSetupActions.test.tsx`。
`e2e/solo-import-race.spec.ts` ではネイティブFileReaderの開始を遅らせ、
リセット後の反映防止と、新旧の読込が逆順に完了した場合を実ブラウザーで検証する。

## 保存デッキ選択後の再確認

保存デッキ一覧を開いた後、別タブで対象のレコードが編集・削除される場合がある。
`useGameBoardSavedDeckPicker` は読込ボタンの押下時に対象IDの現在のレコードを読み直す。

- レコードがない、または一覧表示時から内容が変わっていれば、読込を行わず一覧を更新する。
  更新後の内容を利用者が確認して再度選べるよう、ダイアログは開いたままにする。
  更新日時だけではなく全レコードを比較し、同じ日時の変更も検出する。
- 変更されていない対象だけを、既存の復元・合法性検証で再構築してから一括で渡す。
  能力文・両面情報・関連トークンの補完を維持する。他の保存デッキだけの更新は読込を妨げない。
- 読込時の対象プレイヤーの準備条件と、閉じた後は読み込まない既存の条件を維持する。
  保存レコードの再確認は後述の非同期完了時にも行う。詳細取得の通信先はまだ切り替えない。

所有テストは `src/hooks/gameBoard/useGameBoardSavedDeckPicker.test.tsx`。
`e2e/solo-saved-deck-refresh.spec.ts` は別タブによる名前変更・削除を検証し、
変更時に盤面を保持することと、再選択後の40/10/1枚の読込を確認する。
これは分割取得接続前の入口保護であり、GameBoardの取得量はまだ減らない。

## カタログ取得失敗からの復旧

分割取得接続の前提として、現行カタログにも `loading / ready / error` と明示的な再試行を接続する。

- 失敗時は盤面・対戦セッション・受信イベントを消さず、画面上部のボタンで再取得できる。
  再試行は失敗後だけ許可し、連打・取得中・成功後の呼出しで追加取得しない。自動リロードも行わない。
- 成功時は全体のルール用データと完全な詳細を既存の構築処理で作り、保存デッキにも同じ完全なデータを渡す。
  保存デッキ側だけ失敗したままになる独立した取得は廃止する。
- Inspectorは詳細がない場合の取得中・取得失敗を、不明IDや能力文がないカードと区別する。
  既にある詳細は表示し続け、成功後の未知カードは従来の表示を維持する。
- アンマウント・Strict Modeで破棄された取得の成功や失敗を反映しない。
  同期処理・Reducerへデータの待機やリセットを挟まない。

主な所有テストは `useGameBoardCatalogResources.test.tsx`、表示は `GameBoardCatalogStatus.test.tsx`。
`useGameBoardSavedDeckPicker.test.tsx` は共有結果の到着後に保存デッキを開ける契約を持つ。
`e2e/game-board-catalog-retry.spec.ts` は通信失敗中に開始したソロ対戦を保持したまま再取得する。
これは現行JSONの再試行であり、分割データの版固定・旧版削除時の復旧を実装したものではない。

## 保存デッキ一覧の索引構築の集約

`buildLegalSavedDeckOptions` は、保存デッキごとに全カタログの索引を作り直していた。
復元で1回、インポートの整形で7回となり、デッキD件・カードC件に対して索引構築だけで8×D×Cの処理があった。

- `createSavedDeckRestorer` と `createImportedDeckSanitizer` を一覧処理内で作り、全デッキで共有する。
  全カタログの索引構築は一覧1回につき最大2回になる。保存デッキ0件なら走査せず、
  全デッキに欠損IDがあれば復元用の1回だけで、整形用の索引は作らない。
- 単独の `sanitizeImportedDeckState` も、各セクションと関連トークン補完で1つの索引を共有する。
  既存の単独APIの引数と戻り値、処理順序、関連展開ルールは変えない。
- 共有するのはID検索用の読み取り専用Mapだけ。枚数集計、ルール判定用の状態、
  トークン候補、欠損ID、結果の配列はデッキごとに作る。
- グローバルなキャッシュや配列の参照同一性によるキャッシュは導入しない。
  一覧を更新するたびに索引を作り直し、同じ配列の差し替え・削除も次回の呼出しに反映する。
  これらのfactoryは1回の同期的な処理内で利用し、カタログ更新を跨いで保持しない。

所有テストは `src/utils/gameBoard/gameBoardSavedDecks.test.ts`。
保存デッキ1件・上限の200件の双方で全カタログの走査回数を検証する。
`deckBuilderRules.test.ts` と `deckStorage.test.ts` は、呼出し間の状態分離、

参考計測（2026-10-18、Node、実カード7,684件、構築済みサンプル保存デッキ200件、各3回の中央値）では、
一覧構築は従来の550msから39msとなった。従来実装はmainの4273987を使い、
同じ入力で返った200件の全内容のJSONハッシュが一致することも確認した。
これは特定環境での処理時間の参考値で、ブラウザー上の表示時間や通信量の削減率を保証するものではない。
この変更では通信先・取得量・保存形式・分割取得の接続状況は変わらない。

## 保存デッキ一覧と読込用データの分離

`SavedDeckPickerOption` は保存レコード（カードIDと枚数）、ルール概要、枚数表示だけを持つ。
Hook、ViewModel、ダイアログ、ダイアログHostはこの型を受け取り、展開済みカード配列の
`deckData` を一覧の状態として保持しない。

- `buildSavedDeckPickerOptions` は既存と同じ復元・整形・合法性検証を実施した後、
  各行を表示用データへ絞って返す。検証を省略したり、一覧から無条件に読込可能と判断したりしない。
  検証途中の展開配列を、全行分の戻り値に保持する処理も挟まない。
- `LegalSavedDeckOption` と `buildLegalSavedDeckOptions` は完全なカード配列を返す既存APIとして維持する。
  読込ボタンでは現在の保存レコード・対象プレイヤーの条件を再確認し、選択された1件だけを
  現在の完全なカタログから復元して、その `deckData` を一括で渡す。
- 能力文・両面・関連トークンを一覧の省略データで置き換えない。元レコードの件数表示、
  検索、表示順、ダイアログ操作は維持する。全カタログの索引も一覧ごとに最大2回のまま。
- 保存デッキ0件の早期終了、各区分の欠損IDの除外、更新・削除時の選び直し、
  読込前のカタログ差し替えにも引き続き対応する。

所有テストは `gameBoardSavedDecks.test.ts` と `useGameBoardSavedDeckPicker.test.tsx`。
一覧の正確なフィールド構成と、最新の完全な詳細を復元する契約を別々に検証する。
ダイアログのテストは表示用の3フィールドだけを持つ入力で、表示と読込の配線を確認する。

この変更は一覧が保持する展開済み配列の削減と型の分離であり、カタログの通信先や取得量、
保存形式、P2Pイベント、同期的な読込の順序は変更しない。分割データの取得や非同期読込はまだ接続しない。

## 保存デッキの非同期完了を保護する

`useGameBoardSetupActions.beginDeckImport(target)` は、`isCurrent` と `cancel` を返す。
保存デッキとJSONファイル読込は同じプレイヤー別の操作識別子を利用する。

- 新しい同プレイヤーの読込・同期的なインポート・ローカルリセット確定で以前の操作を無効にする。
  権限喪失・role変更・対象構成の変更・アンマウント後も再利用しない。
  他プレイヤーの操作や、画像と名前だけの更新では取り消さない。
- `isCurrent` は最新の操作権限・準備条件・対象構成を確認する。
  GameBoardの既存の `gameStateRef` を利用し、再描画前の状態変更も参照する。
  古い操作の `cancel` が新しい操作を消すことはない。
- 保存デッキHookは、閉じる・別の対象や選択への変更・カタログ・詳細取得元・roleの変更後に、古い成功も失敗も反映しない。
  完了時に保存レコードを再取得して比較し、変更・削除時は一覧を更新して選び直す。
- 取得した完全なカードから再構築した各区分のID・順序・枚数・補完トークンが、既存の整形結果と一致する場合だけ反映する。
  既知の関連トークンが欠けた部分的な応答ではインポートしない。
- 読込中は重複したLoad操作を無効にし、閉じる操作は維持する。
  有効な操作の失敗はダイアログ内に表示し、明示的な再読込で再試行する。古い失敗は表示しない。

現在の通常経路は既に取得した完全なカタログをPromiseで受け取る。通信は追加せず、
`resolveSavedDeckCards` は今後の版固定詳細取得を差し込むための入口となる。
この段階では新しいカタログ版への復旧、P2P全体のイベント世代管理、分割データへの画面接続は行わない。

所有テストは `useGameBoardSetupActions.test.tsx` と `useGameBoardSavedDeckPicker.test.tsx`。
完了順逆転、取消後の失敗、ローカルリセット、同期読込との競合、最新条件の確認、保存レコード更新・削除、
不完全な関連トークン結果と再試行を検証する。表示は `GameBoardSavedDeckPickerLoading.test.tsx` が担当する。
`e2e/solo-saved-deck-cancel.spec.ts` は実際の通常経路で、Promiseの続きの前に閉じた場合の取消と、その後の正常な40/10/1枚の読込を確認する。

## 次の実装を始める条件と順序

### 保存デッキ用の分割詳細取得（画面は未接続）

`createGameBoardSavedDeckReader(source)` は開いた1バージョンの生成カタログを受け取り、
`loadCards(record)` で保存デッキの全区分に必要な完全なカードを返す。
`useGameBoardSavedDeckPicker` の `resolveSavedDeckCards` に渡せるが、通常画面の取得元はまだ変更しない。

- main/evolve/leader/tokenの参照IDを待機前にコピー・重複排除し、再帰的な関連参照も既存の版固定Readerで取得する。
  枚数と並び順は既存の復元処理で展開する。全カタログの詳細は要求しない。
- 一覧にない保存IDは `UnknownSavedDeckCardsError.cardIds` で通信前に拒否する。
  既存の復元処理と同様、枚数0の参照も存在確認する。HTTP失敗を不明IDに変換せず、
  一部だけ取得できた結果や一覧情報を成功結果として返さない。
- 取得済みカードの全項目を保持し、インポート用のカード・関連参照・両面情報をコピーする。
  入力や検証済みの読み取り専用カタログを書き換えず、呼出し間で可変カードを共有しない。
- 取得グループの共有・検証・失敗キャッシュ破棄は既存Readerが担当する。
  独自キャッシュ・自動再試行・新版や従来JSONへのフォールバックは追加しない。
- この処理は保存レコードや盤面を更新しない。キャンセル、最新保存内容・対象条件の確認、
  一括反映は前段の保存デッキHookが引き続き担当する。

所有テストは `gameBoardSavedDeckReader.test.ts`。全区分、不明ID、関連循環、逆順完了、

`generatedCardCatalogParity.test.ts` は実際の生成物を使い、40/10/1枚のサンプルと、
関連トークン・両面を持つ選択の復元結果を従来の完全カタログと比較する。
失敗後の同じ版での再試行、必要グループだけの取得と正常グループの再利用も検証する。
`useGameBoardSavedDeckPicker.test.tsx` はReaderを差し込んだ場合の失敗・再試行・取消後の反映防止を確認する。

画面接続前には、一覧の検証用入力を画面側でも切り替えること、
対戦・受信イベントを維持したまま詳細表示を復旧すること、
同じ構成へのリセットは後述の目印で識別する。接続・セッション全体の世代管理を代行するものではない。

### 保存デッキ一覧の判定用入力（通常画面の取得元は従来どおり）

`buildSavedDeckPickerOptions` は `readonly DeckRuleCard[]` を受け取る。
`DeckRuleCard` はID・名前・クラス・タイトル・種別・区分・分類フラグ・関連参照のみを持ち、
画像・能力文・両面・能力値には依存しない。凍結された生成一覧を変換や完全なカード型へのcastなしで渡せる。

- 復元・整形・合法性検証は既存処理を共有し、順序や条件を変更しない。
  復元・整形のfactoryは入力カード型を保持する。詳細を補ったふりをしたカードを生成しない。
- 一覧の結果は引き続き保存レコード・概要・保存枚数表示だけで、展開カードを公開しない。
  不明IDの除外、コピー数の制限、関連トークン補完後の検証、表示順と保存時の枚数表示を維持する。
- `DeckState` と復元結果の型には既存の完全なカード型を既定値として残す。
  完全なカタログと空配列を使う既存factoryの型推論も維持する。
  `buildLegalSavedDeckOptions` と単独の完全インポートAPIは完全なカードを必要とする入口として維持する。
- 一覧1回の全カタログ索引構築は引き続き最大2回で、空の保存一覧は走査しない。
  独立したルールの実装や新しいキャッシュ、取得処理は追加しない。

所有テストは `gameBoardSavedDecks.test.ts`。凍結された一覧、詳細項目を読まないこと、
各区分の不明ID、合法性検証と保存枚数表示、関連参照を持つ200件の索引構築を検証する。
`deckStorage.test.ts` は空の既存APIの戻り値が完全なカード型のままであることを型チェックでも確認する。
`generatedCardCatalogParity.test.ts` は実カード全件を使った保存候補、構築・タイトル・クロスオーバー設定、
各区分の不明IDについて従来データとの一覧結果の一致を確認し、manifestとindex以外の取得を禁止して検証する。

この変更は型と共有入力の整理であり、既存処理の実行時JavaScriptは変更しない。
通常のHookはまだ完全なカタログを渡し、選択時の完全な詳細の復元も従来方式を維持する。
初回取得量を減らすための画面側の接続は引き続き別工程とする。

### 同じ構成への相手側リセットから読込を保護する

カードとトークン構成だけの比較では、空の盤面や元の位置へ戻ったデッキへのリセットを識別できない。
`SyncState.lastResetRevision` は最後に受理した `RESET_GAME` のrevisionを記録する省略可能な項目とする。

- 権限を確認したReducerがリセットを受理した場合だけ、更新後のrevisionを記録する。
  通常の操作や受理されないリセットでは変更しない。
- 既存のスナップショットと保存セッションはこの項目も保持する。メッセージ種別・送受信順序、
  スナップショットの受理条件、リセット完了のUI通知は変更しない。
- JSON・保存デッキの共通読込ガードは、この目印も対象構成と比較する。
  スナップショット適用後、Reactの再描画前の完了でも既存のlive refで拒否する。
  古い不正JSONの警告や、古い詳細取得の失敗も表示しない。
- 同じ目印の重複受信、無関係なrevision更新、拒否された古いスナップショットでは新しい読込を取り消さない。
  目印はUndo用チェックポイントへ含めず、カード操作・ターンのUndoでも現在の値を維持する。
- 項目がない旧状態は0相当で比較し、保存データも引き続き受理する。
  項目がある保存データでは、0以上かつ現在のrevision以下の安全な整数であることを検証する。
  この項目だけがある空の部屋を、復元対象の対戦として保存しない。

主な所有テストは `gameSyncReducer.test.ts` と `useGameBoardSetupActions.test.tsx`。
保存デッキの遅い成功・失敗と再試行は `useGameBoardSavedDeckPicker.test.tsx`、
JSONでの送信と旧保存状態の互換性は `gameBoardSnapshot.test.ts` と `gameBoardSavedSession.test.ts` が担当する。
`useGameBoardLogic.test.tsx` は接続モック経由で、ホストのリセットを受け取った同じ処理内で読込が終わる競合と、
その後の新しい読込が古い/重複スナップショットに妨げられないことを確認する。

目印のない旧ホストが行った同一構成のリセットは識別できないため、新しい保護を利用するにはホスト側も更新後の画面が必要となる。
既存の対戦を強制リロードしたり、UI通知を状態変更の根拠として使ったりしない。
この変更も分割カタログの画面接続は行わない。

### 詳細表示の再試行と明示的なカタログ復旧（通常ページは未接続）

`useGameBoardGeneratedCatalogResources(ids, path)` は版固定の生成カタログを開き、同じ取得元から
ルール用メタデータ・保存デッキReader・表示用詳細を組み立てる。
盤面・保存セッション・通信処理は入力として受け取らず、更新や待機を挟まない。

- 初回はmanifestとindexを開いてメタデータを公開し、必要IDの詳細取得は別の表示用Hookで進める。
  詳細の失敗でメタデータを破棄せず、同じ版での `details.retry()` を提供する。
- `refreshCatalog()` は明示操作でmanifestを開き直す。自動更新やページのリロードは行わず、連打もまとめる。
  現在の版がある場合、新しいカタログの検証と現在必要な詳細の取得が成功するまで、以前の版と取得済みの表示情報を公開し続ける。
- その間に対象IDが変わった場合、新しい版で最新のIDも検証してから切り替える。
  新しい版にないIDは通信失敗と区別し、盤面の外部カードやカスタム画像を削除しない。
  取得失敗時は旧版を保持して失敗状態を返し、次の明示操作で再試行する。
- 成功時はカタログ・ルール用メタデータ・保存デッキReaderを一括で切り替え、以前の版の詳細を新しい版の結果として公開しない。
  新版の確認で取得した詳細グループは下位Readerのキャッシュから再利用する。
  パス変更・アンマウント・Strict Modeの破棄された応答は反映しない。
- 表示用Hookの `getDetailStatus(id)` は、取得済み・未要求・取得中・取得失敗・不明IDを区別する。
  別のカードの取得失敗によって、取得済みカードや不明IDを失敗表示にしない。

Inspectorにはこれらの状態と明示的な操作用の任意propsを追加する。
読込中・不明ID・失敗の文言と、同じ版の再試行・カタログの読み直しを区別し、更新中は重複操作を無効にする。
閉じる操作、カスタム画像、能力文が空の完全なカード、取得済みの両面表示は維持する。
新propsを渡さない従来のページの表示・カタログ取得元は維持する。

所有テストは `useGameBoardGeneratedCatalogResources.test.ts`、`useGameBoardGeneratedCardDetails.test.ts`、
`GameBoardGeneratedDetailRecovery.test.tsx`。初回失敗、同版再試行、manifest/新版詳細の失敗、対象ID変更、
パスの往復、アンマウント、Strict Mode、不明IDの再発見とInspectorの操作を検証する。

### 保存デッキHookの入力経路

保存デッキHookは次の2経路を受け取れる。通常画面は引き続き従来経路を使う。

- 従来経路: `catalogCards` に完全なカタログを渡す。既存の任意resolverも維持する。
- 生成経路: `generatedCatalog` に `createGameBoardSavedDeckReader` の結果を渡す。
  Readerが同じ版の `summaries` と `loadCards` を保持する。従来カタログとの同時指定や、
  一覧情報だけを完全なカタログとして渡す入力は型チェックで拒否する。

一覧を開く・検索する段階では一覧の情報だけで既存の復元・整形・合法性検証を行い、詳細を取得しない。
Loadの前に `buildSavedDeckImportSignature` で各区分のID・順序・整形済み枚数・関連トークンを固定する。
これはID配列の文字列表現のみで、対戦へ渡せるカード配列を作成・公開するAPIではない。
選択したデッキの完全な詳細を取得後、従来の `buildLegalSavedDeckOptions` で再構築し、
同じ署名になった場合だけ最新のレコード・操作条件を確認して一括反映する。
不足した結果を一覧情報や従来JSONで補った成功結果として扱わない。

Readerは1つのカタログの間、同じインスタンスを保持する。
版の文字列が同じでもReaderのインスタンスが変わったら待機中の操作を取り消す。
古い要求の成功・失敗・finallyが、新しい要求の状態を変更しない既存の契約も維持する。

主な所有テストは `useGameBoardSavedDeckPicker.test.tsx`。
生成一覧からの表示時に詳細取得しないこと、選択時の完全な能力文・両面・関連トークン、
部分結果からの再試行、Reader交換、保存レコード変更、閉じる操作、live refのリセット保護を確認する。
`gameBoardSavedDecks.test.ts` は一覧からの署名と完全な復元結果の一致、各区分の不明ID、空の合法デッキと不正デッキの区別を担当する。
`generatedCardCatalogParity.test.ts` は実際の生成物で40/10/1枚と関連トークン・両面を含む署名の一致を検証する。
通常ページのデータ取得・詳細表示・対戦通信はこの段階では切り替えない。

### 接続までの順序

1. 【構築処理は分離済み、画面接続は未実施】一覧から作れる判定用メタデータと、完全な詳細が必要な処理を区別する。
   一覧には名前・種別・関連参照・能力値があるが、能力文・両面はない。
   一覧を既存の詳細ビルダーへ渡して空の能力文を成功結果と扱わない。
2. 【比較テスト追加済み】一覧全体による進化ファミリー・リンク判定が従来と一致することを、
   今回の合成例と実データで検証する。選択したデッキだけを基準にファミリーを再構築しない。
3. 【独立処理とテスト追加済み、画面は未接続】ID単位の詳細取得・版固定・失敗時の再試行を独立した処理で実装する。
   GameBoardのためにDeckBuilderのページ選択Hookや操作キャンセル方針をそのまま流用しない。
4. 【JSONと保存デッキの完了ガード・受理済みリセットの識別は実装済み、分割データの操作への接続は未実施】保存デッキ、JSON読込、保存対戦の復元、相手からのイベント・スナップショット、
   トークン生成の各入口について、取得待ち中の順序と対象プレイヤーを守る方式を決める。
   保存デッキ一覧の検証用データを、そのまま対戦用データとして渡さない。
5. 【独立Hook・Inspector拡張は実装済み、通常ページは未接続】対戦中の取得失敗で盤面や受信内容を消さず、未取得詳細を再試行できる設計にする。
   DeckBuilderと同様の再読み込み案内だけでは、進行中の対戦保護の代わりにならない。
   旧版削除時の再接続・復元も含めて設計してから接続する。
6. 【画面接続済み】単体・Hook・通常/本番E2E・Vercel確認で検証する。
   データ待ちで相手との同期が崩れないことを確認し、初回とデッキ読込後の取得量を測る。

追加の外部ストレージ・有料サービス・生成バイナリのGit管理は導入しない。
従来JSONの公開停止や削除は、全利用箇所の移行と配信確認が終わるまで別工程とする。
