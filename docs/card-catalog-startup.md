# 開発サーバー初回読み込みとE2Eの開始条件

## 調査の目的と結論（2026-10-19）

schema 3を見送るPR #237の検証で、通常E2Eの`card-catalog-loading.spec.ts`が一度、
DeckBuilderのファイル入力が5秒以内に有効にならず失敗した。他57件は成功し、対象2回と全件再実行も成功した。
その失敗時点のネットワークトレースは残っておらず、過去の1回の原因を断定することはできない。

新しい開発サーバーで計測したところ、初回manifest応答では生成と`--check`の完了待ちが支配的だった。
従来のPlaywright開始条件はトップページのHTTP応答だったため、カタログ準備の約3秒が、初回テストのUI待機5秒に含まれていた。
この余裕の少なさが環境負荷でタイムアウトし得る要因である。入力準備が停止し続ける不具合は今回の計測では再現していない。

## 計測条件と結果

schema 2、7,684枚・58グループ。Chromium、英語UI、空のlocalStorageを持つ新規ブラウザーコンテキスト。
外部Google Fontsは通常E2Eと同じ既存fixtureの条件で遮断し、カタログ要求は通常E2Eと同じroute.continueで通した。
各試行は専用ポートで起動した新規Viteプロセスを使い、同一プロセスへの再訪も別の新規コンテキストで測った。
ブラウザーのMutationObserverでファイル入力の有効化時刻、Resource Timingで応答終了、PerformanceObserverで長時間処理を記録した。
Viteのディスク上の依存キャッシュは消去していない。各3回の参考計測であり、CIの性能保証値ではない。

| 条件 | 試行1 | 試行2 | 試行3 |
| --- | ---: | ---: | ---: |
| 準備前: 初回manifestの応答時間 | 2,832 ms | 3,159 ms | 2,821 ms |
| 準備前: 画面の入力有効化（ナビゲーション開始から） | 3,780 ms | 4,102 ms | 3,740 ms |
| 同じサーバーへの再訪: 入力有効化 | 893 ms | 869 ms | 841 ms |
| manifest準備後の新規画面: 入力有効化 | 916 ms | 806 ms | 836 ms |

準備後もブラウザー自体は新規コンテキストで、画面の初期化とReaderの検証は実行している。
準備後のサーバー側manifest生成待ちは2,553・2,670・2,752 msで、UIを開く前に完了させた。
従来条件のindex応答は約16〜172 ms、indexの最後の応答から入力有効化までは約217〜421 msだった。
この後半には検証・React描画・draft初期化などが含まれ、個別の処理時間には分解していない。

Pythonの生成と`--check`だけを別に3回実行すると、合計3,159・2,586・2,592 msだった。
`build/cardCatalogArtifacts.ts`の生成→独立検証を待つ実装と、初回manifestの応答時間が整合する。
React Strict Modeでmanifestは2回要求されるが、開発サーバーの既存pending共有により生成は共用される。

## 対応

`playwright.config.ts`のwebServer.urlを`/card-catalog/manifest.json`に変更し、
実際に生成・検証が完了した応答を受けてから通常の機能E2Eを開始する。
開発サーバーは全生成物を独立検証してからmanifestを返すため、このURLでサーバー準備を確認できる。
ブラウザー内のキャッシュやカタログ状態を注入する処理は追加しない。
各テストの5秒のassertionと通常のテスト制限、再試行条件は変更しない。
生成に必要な時間はサーバー準備として残り、アプリや本番の速度改善を意味する変更ではない。

traceは`retain-on-failure`にし、ローカルで再試行0回でも失敗時のネットワーク・DOM・操作記録を残す。
成功時のトレースは保持せず、生成物・トレースをGitには追加しない。
本番buildは生成済みの静的カタログを配信する。アプリ・生成器・配信形式・キャッシュ・保存・P2Pは変更しない。
本番Playwrightは別のpreviewサーバー設定を使うため、開発時の生成待ちはない。

## 検証と再調査

- 初回応答が検証済みの全build生成物と一致する契約は`build/cardCatalogDev.test.ts`が所有する。
- カタログ読み込みと保存デッキ復元の機能契約は`e2e/card-catalog-loading.spec.ts`をそのまま維持する。
- 対象を`npx playwright test e2e/card-catalog-loading.spec.ts --workers=1 --trace on`で実行できる。
- トレースは失敗時に`test-results/`へ残る。既存開発サーバーを再利用する場合、生成器やViteプラグインの更新後は先に再起動する。
- 初回応答そのものを測る場合は、別ポートで新しい開発サーバーを起動し、ブラウザーで開く前にmanifestの最初の応答時間を測る。
  準備後のE2E結果を、開発サーバーの初回生成速度や本番の応答速度として扱わない。

本番のマージ済みデプロイでもschema 2・保存デッキの復元・失敗からの明示的復旧・リセット・画面移動を確認し、pageerrorはなかった。
Safari固有の描画と実機間WebRTCタイミングは今回の調査対象外。
