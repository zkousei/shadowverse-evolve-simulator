# 詳細グループの分割候補の比較

## 今回の範囲

PR #232の計測を使い、商品プレフィックス内の詳細を枚数上限またはUTF-8サイズ上限で分けた場合の取得量を比較する。
`npm run cards:compare:partitions` はメモリー内で比較し、JSONだけを標準出力へ返す。
正本・実際の生成処理・配信形式・Reader・キャッシュ・対戦処理は変更しない。
候補のファイルやバイナリを保存・配信・Git管理しない。

```sh
npm run build
npm run --silent cards:compare:partitions -- --check-output dist/card-catalog --include-probes --deck public/sample-decks/constructed-royal-sample.json --deck public/sample-decks/crossover-royal-witch-sample.json > /tmp/catalog-partition-comparison.json
```

- 既定候補は64/128/256枚と64/128/256 KiB。`--max-cards 64 128`や`--max-bytes 131072`で候補を限定できる。
  片方を指定した場合、未指定の方式の既定候補は追加しない。
- `--deck`は複数指定できる。入力区分とIDは計測ツールと同じ検証を行い、不明ID、不正JSON、重複するシナリオパスは失敗する。
- `--check-output`は現在の実生成物と正本の一致を検証する。指定しなければartifactの事前生成は不要。
- `--include-probes`は一覧の先頭・中央・末尾から最大50 IDと、最大枚数グループの先頭1 IDを追加する。
  フィルター適用後の実画面や合法デッキを再現するものではなく、固定された合成カード集合である。
  すべての集合で関連参照を再帰的に含める。

## 比較モデルと維持する条件

- 元のプレフィックスを越えて混ぜず、元の詳細ファイル内の順序を維持して分割する。上限内のグループは分割しない。
- 全カードの全項目、型、false/0/空文字/欠落、能力文、両面、拡張項目、関連IDをそのまま保持する。
  一覧全体の順序も維持し、候補の`detail_group`だけを変更する。関連循環と重複は一度だけ取得する。
- サイズ上限は非圧縮UTF-8のJSON配列全体（区切りと改行を含む）。1枚だけで超える場合は分割せず、
  `oversizedSingleCardGroups`で明示する。単一カードの内容を削除して上限へ収めない。
- 一覧の参照先文字列、manifestの各descriptor・件数・ハッシュ・サイズ・バージョンの増加もモデルへ反映する。
  詳細だけを小さくして、初回の増加を無視した比較にしない。
- manifest/indexの構造は現在のものを仮定する。分割IDの`@`は既存の商品プレフィックスと衝突しない比較用の目印。
  **候補は現Readerで読める配信artifactではない。** `comparisonOnly: true`を返し、実配信のスキーマと検証は別途設計する。
  将来の実装に必要な追加メタデータなどにより、実際のサイズはこのモデルから変わり得る。
- サイズはファイル単位のgzip合計。キャッシュなしのmanifest/indexを含む。通信回数はファイル数であり、
  最大4件の同時取得枠での所要時間を示さない。画像、JS/CSS、HTTPヘッダー、実配信圧縮、ヒープ量は対象外。

| 64枚 | 154 | 247,257 | 15 / 303,641 | 9 / 277,347 | 928,297 |

128枚上限では、最大グループの1 ID取得で詳細624枚が128枚へ減り、通信回数を増やさずに軽くなる。
一方、末尾50 IDでは通信が12回から20回へ増える。これらは固定集合の比較であり、実際のページ移動時間は測定していない。

## 判断と次の作業

この段階では一律の細分化を採用しない。改善する集合と悪化する集合があり、単純な上限変更だけでは全体の改善を確認できない。
次の候補は大きなグループだけを対象とする分割などに絞り、初回増加・デッキ読込・ページ相当集合・1枚取得を再比較する。
2つのサンプルと合成集合だけで全デッキへの効果を断定しない。

実配信へ進む前には、Readerが商品プレフィックスと詳細グループを同一視する検証を見直す必要がある。
その際も元のデータは分割せず、ビルド時に生成する方式を維持する。
全件互換性、関連参照、同時取得上限、失敗・再試行、版固定、保存デッキ、対戦中の復旧を先にテストで保護し、
実データのサイズ比較・通常/本番E2E・Vercel Previewの確認が成功してから採用を判断する。

## テスト所有先

`tools/card_data/compare_partitions_test.py`が、全項目・参照・順序の維持、上限境界、UTF-8、単一カード超過、
同一商品の増加、初回メタデータを含むサイズ、複数集合、空データ、再現性と入力非変更を担当する。
`tools/python_entrypoints_test.py`は、CLI起動・実生成物の検証・標準出力・終了コード・成功/失敗時にモデルやファイルを書かないことを担当する。
実行は`npm run test:python`。アプリの実行時処理を変更しないため、この比較ツールの追加で画面E2Eの契約は増やさない。


## 大きなグループに限定した追加比較

一律分割の副作用を抑えるため、元の詳細ファイルが閾値を超える場合だけ分割する比較オプションを追加した。
この追加もメモリー内のモデルだけを扱い、配信・実生成処理・Readerは変更しない。

```sh
npm run --silent cards:compare:partitions -- --check-output dist/card-catalog --include-probes --deck public/sample-decks/constructed-royal-sample.json --deck public/sample-decks/crossover-royal-witch-sample.json --max-bytes 131072 --selective-bytes 262144:65536 262144:131072 393216:131072 393216:262144 > /tmp/catalog-selective-partition-comparison.json
```

`--selective-bytes THRESHOLD:TARGET`はUTF-8の非圧縮bytesで指定する。閾値・分割先の目安は正の整数で、閾値は目安以上とする。
元ファイルが閾値と等しい場合も含め、閾値以下のグループは分割せず、内容とグループIDを維持する。
そのため全ファイルがTARGET以下になる方式ではない。バージョン全体のURL・ハッシュは、将来の実配信で別途検証する。
閾値をTARGETと同じ値にすれば従来の一律サイズ上限と同じモデルになる。

選択的な候補だけ指定した場合は、現行とその候補だけを出力する。一律の候補とも組み合わせられる。
新しいオプションを指定しなければ、既存の既定6候補と出力は変わらない。同じ実データで、変更前のJSON出力とのバイト単位一致を確認した。

選択的な候補には次の項目も返す。

- `eligibleSourceGroups`: 元ファイルのサイズが閾値を超えたグループ。
- `splitSourceGroups`: 実際に複数のファイルに分かれた元グループ。対象でも1枚だけなら分割できない場合がある。
- `groupsAboveTargetBytes`: TARGETを超える結果ファイル数。対象外として維持したグループも含み、すべてが上限違反を示す値ではない。
- `oversizedSingleCardGroups`: 対象グループ内で1枚だけでもTARGETを超える例外数。
  閾値以下で意図的に維持した単一カードは、この例外に数えない。

### 同じ実データでの結果

| 方式 | 対象の元グループ | 分割後グループ数 | 初回 gzip bytes | ロイヤル：回 / gzip bytes | クロスオーバー：回 / gzip bytes |
| --- | --- | ---: | ---: | ---: | ---: |
| 現行 | — | 58 | 239,645 | 9 / 319,187 | 6 / 269,312 |
| 一律 → 128 KiB | 128 KiB超の全グループ | 91 | 242,911 | 12 / 315,333 | 8 / 275,921 |
| 256 KiB超 → 64 KiB | CP04, PR | 69 | 240,598 | 13 / 326,014 | 10 / 276,139 |
| 256 KiB超 → 128 KiB | CP04, PR | 63 | 240,145 | 10 / 320,317 | 8 / 273,155 |
| 384 KiB超 → 128 KiB | PR | 61 | 239,953 | 9 / 319,495 | 6 / 269,620 |
| 384 KiB超 → 256 KiB | PR | 59 | 239,799 | 9 / 319,341 | 6 / 269,466 |

「384 KiB超 → 128 KiB」の対象は現在PRグループだけで、全体58グループが61グループとなる。
初回の増加は308 gzip bytes（約0.13%）。2つの実デッキの通信回数は維持され、合計gzip量はいずれも308 bytes増える。
全詳細を読む場合は794,734から799,655 gzip bytesへ増える。

同候補での合成集合を比較すると次のようになる。

| 合成集合 | 現行：回 / 詳細取得枚数 / gzip bytes | 限定分割：回 / 詳細取得枚数 / gzip bytes |
| --- | ---: | ---: |
| 一覧先頭50 ID | 6 / 872 / 306,419 | 6 / 872 / 306,727 |
| 一覧中央50 ID | 5 / 320 / 262,044 | 5 / 320 / 262,352 |
| 一覧末尾50 ID | 12 / 2,385 / 417,787 | 14 / 2,218 / 408,820 |
| 最大枚数グループの1 ID | 3 / 624 / 285,616 | 3 / 193 / 253,248 |

最大グループの1 ID取得では通信3回を維持し、詳細624枚が193枚、合計gzip量が約11.3%減となる。
ただし末尾50 IDでは12回から14回へ通信が増える。これらは空キャッシュのサイズモデルで、実際の所要時間は未測定である。
すべてのグループを128 KiB以下にはせず、現データでもTARGETを超えるファイルは29個残る。対象内の単一カード超過は0件だった。

### 次の実装候補と開始条件

実配信の次の検証候補を「384 KiB超 → 128 KiB」に絞る。現在のPRグループ名を特別扱いする方式ではなく、
他の商品も将来閾値を超えたら対象となる一般的なサイズ条件である。今回の比較追加で採用・配信は行わない。

実装は次の順序で進める。

1. 商品プレフィックスと詳細グループを区別する配信仕様を定め、Readerの検証と旧形式の読み取りをテストで保護する。
2. ビルド時の生成処理へ限定分割を接続し、全カード・関連参照・順序・欠落/false/0・両面が従来と一致することを確認する。
3. 同時取得4件、重複取得の共有、失敗・タイムアウト・再試行、版固定、保存デッキ、対戦中の復旧を維持する。
4. 実artifactで初回・実デッキ・合成集合を再測定し、通常/本番E2E・Vercel Previewで挙動を確認してから採用する。
   末尾集合の通信増加を含む所要時間は、この段階で確認する。

元のJSONを分割せず、ビルドで生成する方針と、生成バイナリをGitへ追加しない運用を維持する。
今回の新しい契約の所有先も`compare_partitions_test.py`と`python_entrypoints_test.py`。
閾値の直前・等値・超過、非対象グループの内容保持、単一カード例外と意図的なTARGET超過の区別、将来の増加、
不正な閾値、従来候補との併用、成功/失敗時のファイル非変更を検証する。

## Reader対応の進捗

schema 3の[配信形式とReader契約](card-catalog-schema3.md)を定義しました。Readerを先行対応させ、その後に通常生成もschema 3へ切り替えました。
生成器・検証器も対応しました。以下は実生成の確認結果です。比較CLIは引き続き比較専用です。
分割済み入力も商品単位に再結合してから候補を計算し、二重の分割名を作りません。

## 実生成の検証

schema 3の通常生成では384 KiB超の商品だけを128 KiB目標で分割する。
現データ7,684枚では、PRの624枚が193・167・167・97枚の4ファイルになり、58→61グループになる。
他の57商品の詳細ファイルは変更前とバイト単位で一致し、全カードの全項目・全体の順序・関連参照も維持する。

変更前schema 2と実生成schema 3のgzipサイズの比較（バイト）:

| 対象 | 取得数 前→後 | gzip 前→後 |
| --- | --- | --- |
| manifest＋index | 2→2 | 239,645→239,956 |
| PR先頭1枚（manifest＋index含む） | 3→3 | 285,616→253,251 |
| ロイヤルサンプル | 9→9 | 319,187→319,498 |
| クロスオーバーサンプル | 6→6 | 269,312→269,623 |
| index末尾50 ID（合成集合） | 12→14 | 417,787→408,823 |

初回は311バイト（約0.13%）増え、PR先頭1枚の取得は約11.3%減る。
最後の合成集合では転送量が減る一方、リクエストが2件増える。実際の待ち時間が同率で改善する保証はない。
過去の比較モデルの308バイト増との3バイトの差は、実生成ではschema 3を使用するためのmanifest gzip差である。

Reader・キャッシュ・取得キュー・画面・保存・P2P処理はこの生成器対応では変更しない。
Pythonの境界値・再結合・更新・破損検出、実データReaderの全件一致、Vite生成、ブラウザーからの実分割ファイル取得を検証する。
