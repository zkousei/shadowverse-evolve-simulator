# カードカタログの生成・互換性検証

DeckBuilderとGameBoardはビルドで生成した分割カタログを読み込みます。
`public/cards_detailed.json` と `public/cards_preview.json` は生成・更新ツールの入力として維持します。
未使用の旧HTTP取得APIと旧GameBoard Hookは削除済みです。元JSONの公開配信は維持しています。
保存形式とP2P通信形式は変更していません。
通常のビルドでは、後述の手順で検証済み生成物を追加します。

GameBoardの接続方式とテストについては[分割取得の移行記録](game-board-catalog-migration.md)を参照してください。

## 実行方法

リポジトリのルートで実行します。外部通信・追加のPythonライブラリは不要です。

```sh
npm run cards:audit:all
npm run cards:generate:catalog
npm run cards:check:catalog
```

入力は発売済み・先行公開の既存JSONです。更新ツールを実行した後は、再度生成して検証します。
`cards:check:catalog` は生成物を一切書き換えず、不足・古いデータ・改変を検出すると終了コード1を返します。
初回は生成物がないので、先に `cards:generate:catalog` を実行してください。
生成・検証の正常終了は0、不正な入力やファイル操作の失敗は1です。

出力先はGit管理対象外の `artifacts/card-catalog/` です。
`public/` の外なので、この作業用ディレクトリ自体はビルド・公開に含めません。
ビルド時はこのディレクトリを使わず、一時ディレクトリで独立に生成します。
手動生成コマンドだけではアプリの取得先は変わりません。DeckBuilderの接続方式は後述します。

入力・出力はオプションで指定できます。

```sh
python3 -m tools.card_data.generate_catalog \
  --released public/cards_detailed.json \
  --preview public/cards_preview.json \
  --output /tmp/card-catalog-review
python3 -m tools.card_data.generate_catalog --output /tmp/card-catalog-review --check
```

入力ファイルを含むディレクトリは出力先に指定できません。
別用途・不正・未対応スキーマのmanifestがある出力先も、上書きせず拒否します。

## ファイル形式（schemaVersion: 2）

```text
artifacts/card-catalog/
  manifest.json
  versions/<catalogVersion>/
    index.json
    details/BP01.json
    details/BP02.json
    ...
```

- `manifest.json`: スキーマ・カタログのバージョン、件数、ファイル参照、SHA-256、サイズを記録します。
- `index.json`: 統合後の並び順を維持した圧縮表現の一覧です。読み込み時に従来と同じオブジェクト一覧へ展開し、各行の `detail_group` からmanifestの詳細参照を引きます。
- `details/*.json`: 各カードの全項目を保持したJSON配列です。現在の弾フィルターと同じIDの先頭部分でグループ化します。
  ファイル名に使えるグループは英数字とアンダースコアのみです。不正な値は明示的に拒否します。

schema 2のindexは、`encoding: "rows-v1"`、`fields`、`rows`の3項目を持ちます。
`fields`は下表の19項目と末尾の`detail_group`を並べた固定ヘッダーです。
各行は存在する項目のビットマスクと、そのヘッダー順に並ぶ値を保持します。
項目名の繰り返しだけを取り除き、項目の欠落・空文字・false・0・関連参照・順序を区別して保存します。
マスクは20ビット以内の整数で、ID・名前・グループのビットは必須です。
未知のエンコーディング、異なるヘッダー順、行の値の過不足、未定義ビットは拒否します。
展開後も既存の件数・型・関連参照・詳細との投影一致・凍結の検証を行います。
一覧を完全な詳細として扱うAPIや、保存・P2Pデータの形式は変更しません。

新しいReaderはschema 1のオブジェクト配列も読み込みます。schema 2でschema 1の配列を推測して読むことはありません。
生成ツールは既存のschema 1 manifestがある作業ディレクトリも受け付け、新しいバージョンを検証してからmanifestを切り替えます。
旧バージョンのファイルは上書きしません。ビルドでは従来どおり現在版だけを配信します。
**schema 1しか読めない更新前のアプリ画面は、新manifestを取得すると再読み込みが必要です。**
新しいアプリでは、保持しているschema 1カタログからschema 2への明示的な復旧も可能です。

軽量一覧には次の項目を、入力に存在する場合だけ保持します。

| 用途 | 項目 |
| --- | --- |
| 識別・表示 | `id`, `name`, `image`, `catalog_status` |
| フィルター・同一性 | `class`, `title`, `type`, `subtype`, `rarity`, `product_name`, `cost` |
| 判定用情報 | `atk`, `hp`, `card_kind_normalized`, `deck_section`, `is_token`, `is_evolve_card`, `is_deck_build_legal`, `related_cards` |

`ability_text`・`faces`・未知の拡張項目は軽量一覧に含めませんが、詳細にはそのまま保存します。
文字列、数値、真偽値、空文字、未定義項目の有無を意図せず変換・補完しません。
発売済みのIDを優先し、先行公開のみのカードを後ろに追加する既存の統合規則を維持します。
同名の別IDは削除しません。各入力内の重複IDと、統合後の関連カード参照切れはエラーにします。

**軽量一覧は完全なカードデータの代替ではありません。**
そのまま保存・出力・対戦用データとして使わず、必要な詳細を取得・検証してから操作します。
分類・ルールは生成時に再計算せず、既存の正本の値を維持します。分類自体の監査は既存の `cards:audit:all` が担当します。

## 再現性と確定手順

JSONはUTF-8・キー順固定・compact形式です。カード配列の順序は変えません。
カタログバージョンはスキーマと生成データのSHA-256から決まり、生成時刻を含みません。
manifestは決定的なgzip推計値も含むため、同じPython/zlib環境での再実行で同じ内容になります。

1. 入力を読み、形・重複・参照を検証します。
2. メモリ上で一覧・詳細を生成し、再結合が全項目・順序まで一致することを検証します。
3. 出力先と同じファイルシステムの一時ディレクトリに書き、全ファイルを照合します。
4. 検証済みのバージョンディレクトリを確定します。
5. 入力が生成中に変わっていないことを再確認し、最後にmanifestだけを置き換えます。

既存のバージョンは上書きしません。破損があれば自動修復せずエラーにします。
途中失敗時には以前のmanifestと参照先を維持します。manifest更新前の失敗では、参照されない新バージョンが残る場合があります。
旧バージョンや参照されないバージョンを自動削除する処理は含めていません。

`bytes` は実ファイルのバイト数、`gzipBytes` は標準gzipによる推計です。配信時の圧縮設定を確認した値ではありません。
比較基準の `report.fullCatalog` は、統合後の全カードを同じcompact形式で出力したサイズです。
詳細グループをすべて取得すると、分割前より通信量が増える場合があります。
DeckBuilderは一覧と表示ページに必要な詳細から開始し、必要なグループを追加取得します。

### schema 2でのサイズ比較

7,684件の同じ一覧を比較すると、オブジェクト配列の4,606,820 bytes / gzip 272,018 bytesから、
圧縮表現の2,986,107 bytes / gzip 235,920 bytesへ縮小しました（非圧縮約35%、gzip約13%減）。
詳細JSONの内容は変わらず、比較用の従来一覧サイズはmanifestの`report.objectIndex`へ記録します。
これはファイルサイズの比較で、Vercelの実際の配信圧縮やキャッシュを含む転送量の実測ではありません。

Nodeで35回実行し最初の5回を除いた中央値の参考値は、従来JSONの解析が約8ms、圧縮JSONの解析と展開が約13msでした。
端末や負荷で変わるためブラウザー全体の描画時間を示す値ではありません。展開後の一覧の項目数・形は変わりません。
Python生成コードを変更した際は、開発サーバーを再起動して開発用生成物も更新してください。

## 分割データ取得処理

`src/utils/card/generatedCardCatalog.ts` に、生成物を読む独立した取得処理を追加しています。
DeckBuilderは後述のHookを経由してこの取得処理を呼び出します。
GameBoardも生成カタログを利用します。保存・通信形式は維持しています。

```ts
const catalog = await openGeneratedCardCatalog('/card-catalog');
// ここでは manifest と軽量一覧だけを取得する。
const summaries = catalog.index;
// 指定IDの順序・重複を維持して完全な詳細を返す。
const cards = await catalog.loadCards(['BP01-001']);
// 関連カードを再帰的に含める場合は明示的にこちらを使う。
const cardsAndRelated = await catalog.loadCardsWithRelated(['BP01-001']);
```

上記パスは本番ビルドの配信先です。`artifacts/card-catalog/` 自体は公開されません。
開発サーバーでも同じパスで生成・配信します（後述）。公開時の配信確認には本番ビルドとpreviewも使います。
取得には `fetch`・`TextEncoder`・`TextDecoder`・Web Crypto の SHA-256 が必要です。
ブラウザーでは HTTPS または localhost など、Web Crypto が利用できる環境で使います。

### 保証する範囲

- manifest は再検証を要求して取得し、開いたインスタンスはそのバージョンに固定します。
  別バージョンに更新するには、新しいインスタンスを開きます。
- ファイル参照は指定ディレクトリ配下の当該バージョンの固定パスだけを許可します。
  未対応スキーマ・不整合な件数・ファイルハッシュと一致しないバージョンを拒否します。
- 一覧・詳細はバイト数と SHA-256 を確認してから解析します。
  一覧の重複ID・参照切れ・詳細グループの不整合、詳細の不足・余分なID・一覧との値の不一致も拒否します。
- アプリの既存型に合わない既知フィールドや両面情報は拒否し、値を変換・補完しません。
  未知の拡張項目は詳細に保持します。画像が入力にない場合も補完しないため、返却型でも省略可能です。
- 同じインスタンスの同じ詳細グループは、取得中の処理と検証済み結果を共有します。
  失敗したグループはキャッシュから外し、次の呼び出しで再試行できます。
  インスタンスをまたぐグローバルなキャッシュや永続キャッシュは作りません。
- 一覧と検証済みの詳細は型でも区別し、一覧を完全な詳細として渡すと型検査で失敗します。
  型の識別のためにJSON・保存データへ項目を追加することはありません。
- 返却データはネストした項目も凍結し、共有データの書き換えを防ぎます。
- `loadCards` は指定されたIDだけを、呼び出し時の順序・重複を維持して返します。
  `loadCardsWithRelated` は指定IDを重複除去した後、関連参照を順に辿って追加し、循環参照でも停止します。
- 同じカタログインスタンスの詳細取得・検証は、複数の `loadCards` / `loadCardsWithRelated` 呼び出しを通して最大4件まで同時実行します。
  未取得のグループは要求順に待機し、同じグループの取得中Promiseと検証済みキャッシュを引き続き共有します。
- 詳細取得の期限は開始後30秒です。待機列にいる時間を含めず、本文の受信が止まった場合も期限切れで中止し、
  後続の取得へ枠を渡します。失敗グループはキャッシュから外し、明示的な再試行で同じ版から取得し直せます。
  成功・失敗・期限切れ・同期的な例外のいずれでも枠とタイマーを解放します。
- この制限はカタログインスタンス単位です。新版への明示的復旧で開く別インスタンスには独立した取得枠があります。
  盤面イベント・同期受信を待機列へ入れず、表示用データだけを対象にします。
- 複数グループの一部が失敗すると呼び出し全体を失敗とし、部分的な配列を返しません。
  その際、既に検証できたグループは再利用できます。デッキ状態への反映は行いません。

## 取得状態を扱うHook

`useDeckBuilderGeneratedCatalog` はmanifestと一覧の取得状態を扱い、
`useDeckBuilderGeneratedCardDetails` は1つの選択に必要な完全な詳細の取得状態を扱います。
DeckBuilderがこれらを利用します。保存形式と対戦処理は変更しません。

```ts
const resource = useDeckBuilderGeneratedCatalog();
const catalog = resource.status === 'ready' ? resource.catalog : null;
const details = useDeckBuilderGeneratedCardDetails(catalog, selectedIds);
// 一覧: resource.status === 'ready' のとき resource.catalog.index
// 完全な詳細: details.status === 'ready' のときだけ details.cards
```

- 一覧取得は `loading / ready / error`、詳細取得は `idle / loading / ready / error` を返します。
  `ready` 以外では以前のカタログ・カード配列を成功結果として公開しません。
  詳細が `ready` の場合だけ、検証済みの完全な詳細とカタログのバージョンを返します。
- 詳細は指定IDだけを取得します。関連カードも必要な場合は第3引数を明示的に `true` にします。
  同じ内容のID配列は再描画だけでは再取得せず、指定順序と重複は既存の取得処理に従います。
- 選択の変更・解除、カタログ切り替え、再試行、アンマウント後の古い成功・失敗は反映しません。
  AからBを経てAへ戻る場合も新しいリクエストとして扱い、最初の結果を復活させません。
  他の利用箇所と共有する詳細取得の通信自体は中断しません。
- 取得失敗では部分配列を返さず、エラーを返します。自動再試行や画面の自動再読み込みは行いません。
  `details.retry()` は同じカタログ・同じ選択での再試行であり、最新版へ自動で切り替えません。
  `resource.retry()` はmanifestから開き直す明示操作なので、最新版へ変わる可能性があります。
- これらのHookはデッキの追加・保存・復元・下書き書き込みを実行しません。
  詳細Hookは最新の選択だけを表示する用途です。連続クリックでカードを追加する操作のキューとして
  使用すると操作を落とし得るため、その用途では利用せず、画面接続時に別の処理とテストを用意します。

画面では、以下の方法で完全な詳細が揃ってから状態を反映し、
失敗時の案内と再読み込み前の編集中データ保護を行います。

主なテスト所有先は `src/hooks/deckBuilder/useDeckBuilderGeneratedCatalog.test.ts` と
`src/hooks/deckBuilder/useDeckBuilderGeneratedCardDetails.test.ts` です。
応答順の逆転、選択解除、再選択、カタログ切り替え、明示再試行、Strict Modeの再実行を検証します。
既存の生成物・取得・実データ互換性テストは引き続き取得内容の整合性を検証します。

## ローカル開発での分割データ検証

`npm run dev` と `npm run dev:dummy` でも `/card-catalog/manifest.json` と、
そのmanifestが参照する一覧・詳細を取得できます。DeckBuilderがこのパスを利用します。
開発サーバーの起動時には生成せず、この名前空間の有効なGET/HEADへの初回アクセスで生成します。

- 本番ビルドと共通の生成処理を使い、空の一時ディレクトリで生成して独立した `--check` を通します。
  全ファイルを読み取り、一時ディレクトリを削除してから検証済みの結果をメモリ上に保持します。
  `public/`、`dist/`、作業用artifactsやGit管理ファイルには生成物を書きません。
- 正本2件の内容ハッシュをアクセス時に確認します。ファイルのサイズ・更新日時が同じ編集も検出し、
  内容が変われば再生成します。同時アクセスは生成中の処理を共有します。
- 生成後に入力が変わった場合、不正JSON、参照切れ、入力の欠損、Python起動失敗、
  `public/card-catalog` との競合では503と `Cache-Control: no-store` を返します。
  以前のデータやSPAのHTMLへ代替せず、原因を修正した後のリクエストで再試行できます。
- 配信するのは最新版のみです。正本変更後の旧版URLや不正パスは404になります。
  正本が不正な状態では、有効な形式のURLにも生成失敗の503を返します。
  成功したJSONは本番同様 `public, max-age=0, must-revalidate` を指定します。
- この名前空間のGET/HEAD以外は405です。この名前空間以外の静的ファイル・従来JSON・APIの配信は変更しません。

開発サーバーは正本の編集をそのまま再生成へ反映するため、取得中の正本変更はエラーになり得ます。
ファイルの保存を完了してから再試行してください。Vercelのようなデプロイ単位の固定配信とはこの点が異なります。
開発用のオンデマンド生成時間を、本番の静的配信時間と比較しないでください。

主なテスト所有先は `build/cardCatalogDev.test.ts` です。
実HTTPで本番ビルドとのバイト一致、正本更新、失敗後の再試行、同時取得、生成中の正本変更、
HEAD、既存経路の維持を検証します。
`e2e/generated-card-catalog.spec.ts` は実ブラウザーで既存の取得処理を呼び出し、
一覧と必要な詳細グループだけを取得することを確認します。

## ビルド時の配信準備

`build/cardCatalog.ts` のViteプラグインは `npm run build` と `npm run build:dummy`
で動作します。**ビルド環境にPython 3が必要**です。追加のPythonライブラリ・外部通信は不要です。
`npm run dev` / `dev:dummy` 自体の起動時には生成しません。
開発中にDeckBuilderを開くとカタログへアクセスするため、Python 3が必要です。
初回アクセス時と正本変更後のアクセス時に生成・検証します。
生成・検証の分だけビルド時間は増えます。負荷次第でプラグインの所要時間警告が出る場合があります。

1. ビルドごとに空の一時ディレクトリを作り、既存の正本JSONから生成します。
2. 独立した `--check` で、生成物と入力が一致することを再確認します。
3. manifestと参照ファイルを全て読み取り、Viteのアセットとして `dist/card-catalog/` に追加します。
4. 成功・失敗のどちらでも一時ディレクトリを削除します。

生成・検証・読取の失敗はビルドを失敗させます。以前の生成物への代替はしません。
`public/card-catalog` は生成物と競合するため、存在した場合はビルドを拒否します。
元のJSON・作業用artifacts・保存データは書き換えません。
公開システムはビルドが正常終了した場合だけ成果物を公開する必要があります。

配信するのはmanifestと、そのmanifestが参照する**今回の1バージョンだけ**です。
全詳細も配信物に追加するので、デプロイ全体のファイル量は増えます。
DeckBuilderは必要な一覧・詳細だけを要求し、全詳細を一括取得しません。

`vercel.json` ではカタログの名前空間をSPA向けrewriteから外します。
既存ファイルは静的ファイルとして配信され、欠損ファイルは404になります。
現段階はmanifest・バージョン別ファイルの両方を毎回再検証する設定です。
存在しないバージョンの404まで長期キャッシュされるリスクを避けるため、
immutable・長いmax-ageは付けません。
API・既存画面のrewriteは維持します。
Vite previewにもカタログ限定のヘッダーと欠損時404を追加しますが、
これはVercelの実装を再現するものではありません。Vercelの404本文はpreviewと異なります。

### 本番へのマージ前の必須条件

ローカルで成功していても、ビルド環境へのPython依存と配信設定を追加するため、
この変更を本番へマージする前に以下をVercelプレビューで確認します。

- VercelプレビューでPython 3を含む通常ビルドの成功を確認する。
- manifest・一覧・詳細のHTTPステータス、Content-Type、実際のCache-Controlとハッシュを確認する。
- 欠損ファイルがHTMLの200にならず、404になることを確認する。
  存在しないバージョンへの応答が長期キャッシュされないことも確認する。
- 既存画面への直接アクセス、保存デッキの復元、API経路を確認する。

### 公開更新後の取得失敗と復旧

- **公開更新後に旧版の取得が失敗したら、再読み込みで最新版へ切り替える。**
  旧版の永続保持・Git履歴からの再生成・外部ストレージは導入しません。
  ハッシュ付きURLは新旧の混在を防ぐ識別子であり、旧版の保持を保証するものではありません。
  更新前から開いている取得インスタンスは、未取得の旧詳細を要求すると404になり得ます。
  取得処理はエラーを返し、最新版の詳細を旧一覧へ暗黙に混ぜません。
  DeckBuilderでは取得失敗時に再読み込みを案内し、下書きの初期化・確認中は既存の下書きを維持します。
  編集中なら400msの自動保存を待たず、再読み込み前に同期保存・読み戻し検証します。
  保存が失敗した場合は再読み込みを中止します。

今回のローカルテストはVercelへの公開・実環境検証の代替にはなりません。
GameBoardの画面接続と復旧フローは `game-board-catalog-migration.md` を参照してください。

## Gitで管理する範囲

Gitには正本JSON・生成コード・テスト・文書を保持します。
生成済みの一覧・詳細・圧縮アーカイブや、版を保持するための台帳はコミットしません。
`dist/` と作業用の `artifacts/card-catalog/` は `.gitignore` の対象です。
カード更新時に履歴を記録する追加コマンドは不要で、ビルドがその時点の正本から最新版を生成・検証します。

手動生成ツールは同じ作業ディレクトリ内に過去版を残すことがありますが、
ビルドは毎回空の一時ディレクトリを使うため、それらを配信物へ取り込みません。
この方針で外部ストレージや追加サービスは必要ありません。

## DeckBuilderの分割読み込み

- 一覧データで検索・絞り込み・並び順・ページ数・保存デッキの検証表示を計算します。
  表示ページのカードと関連カードの完全な詳細を取得してから、そのページのカード操作を有効にします。
  既に検証済みのページ・絞り込み結果はメモリ上の詳細を再利用します。
- 通常の追加・削除は同期処理です。連続した追加クリックを非同期取得の完了順で入れ替えず、
  追加時には最新のデッキ状態でコピー数・構築制限を再検証します。
- JSON/DeckLogインポート、保存デッキの読み込み・出力、下書きと保存済み基準の復元は、
  必要な既知IDと関連カードの全詳細が取得できてから既存のサニタイズ・復元処理へ渡します。
  一覧データをデッキへ保存しません。不明ID・外部カードの扱いは既存ルールを維持します。
- インポート・読み込み・保存済みデッキの出力は同時に1件だけ処理します。
  待機中は保存・インポートなどを無効にし、名前・ルール変更、削除、リセットなどの編集があれば
  古い操作結果を破棄します。失敗した操作で現在のデッキを部分的に置き換えません。
  詳細取得中に保存レコードや下書き自体が別の場所で変更された場合も、古い復元結果は採用しません。
- 取得失敗時に従来JSONへ自動で切り替えて新旧を混在させません。
  同じ版のページ詳細は明示的に再試行でき、旧版が削除されている場合は再読み込みで最新版を開きます。
  下書きの取得失敗では初期化済みにしないため、自動保存が既存の下書きを削除しません。
- 明示的な再読み込みでは、未完了の遅延保存を止めて現在の下書きを同期保存・読み戻し検証します。
  初期化前・復元確認中の既存下書きは上書きせず、保存に失敗すれば再読み込みを中止します。
- 画面接続を切り戻す場合は、この接続変更をrevertして再デプロイします。
  元のJSONと保存形式は維持しているため、切り戻しで保存形式の移行は不要です。

主なテスト所有先:

- `generatedDeckBuilderCatalog.test.ts`: 一覧と完全な詳細の分離、関連取得、キャッシュ、ID抽出。
- `useDeckBuilderCatalogAction.test.ts`: 全件成功後の反映、同時操作防止、古い成功・失敗の破棄。
- `useDeckBuilderSessionTracking.test.ts`: 下書き詳細の取得待ち・失敗・リセット後の破棄。
- `reloadDeckBuilder.test.ts`: 再読み込み前の同期保存、既存下書きの保護、保存失敗時の中断。
- `DeckBuilder.test.tsx`: 既存の画面仕様と、取得失敗・リセット・ページ再試行の統合。
- `e2e/deck-builder-catalog-update.spec.ts`: 旧詳細404後に実際に再読み込みし、直前の編集を新版で復元。
- `e2e/production/catalog-delivery.spec.ts`: 本番配信で従来JSONを要求せず、一部の詳細だけを取得。


## カード増加時の取得量と一覧項目の計測

`npm run cards:measure:catalog` はビルドと同じ生成処理をメモリー内で実行し、計測結果のJSONを標準出力へ返す。
正本・生成物・保存デッキ・アプリ設定を書き換えず、出力ファイルも作らない。Python標準ライブラリだけを使う。
過去のレポートや生成バイナリをGitへ追加する必要はない。

```sh
# 現在の正本から計測する（artifactの事前生成は不要）
npm run cards:measure:catalog

# ビルドの生成物が正本と一致することも検証し、サンプルの必要グループを計測する
npm run build
npm run --silent cards:measure:catalog -- --check-output dist/card-catalog --deck public/sample-decks/constructed-royal-sample.json > /tmp/catalog-size-report.json
```

- `initial`: 空のキャッシュからmanifestとindexを読む場合。
- `selected`: エクスポートしたJSONのmainDeck/evolveDeck/leaderCards/tokenDeckのIDと、再帰的な関連参照を読む場合。
  重複・関連循環は一度だけ取得し、manifest/indexに必要な詳細グループを足す。`--deck`省略時はinitialと同量となる。
  不正な区分・不明IDを無視して小さく見積もることはせず、終了コード1で失敗する。内部保存用の枚数付き形式は対象外。
- `all`: manifest/indexと全詳細グループを読む場合。
- `requests`: キャッシュなしで必要なファイル数。リトライ・画像・JS/CSS・対戦通信は含めない。
- `bytes` / `gzipBytes`: 実際に生成する各ファイルのUTF-8サイズと、ファイルごとのgzipサイズの合計。
  Vercelの実測転送量、Brotli、HTTPヘッダー、キャッシュ、所要時間、JavaScriptヒープ量は示さない。
- `fetchedCards`: 詳細グループに含まれる全カード数。必要なID以外のカードも同じグループなら取得するため、
  `uniqueRequestedCards + relatedCards`より大きくなり得る。一覧のカード数は含めない。
- `indexFields`: 項目ごとの存在件数・JSON値の種類数・値だけのUTF-8合計。値の型・false・0・空文字・欠落を区別する。
  行マスク・共通ヘッダー・区切りは除くため、`valueBytes`を足してもindex全体のサイズにはならない。
  同じ値が多いことだけで、圧縮後にも同じ割合で削減できるとは判断しない。

現データ7,684枚、58グループでの再現結果は次のとおり。

| シナリオ | ファイル数 | 詳細として取得する枚数 | bytes | gzip bytes |
| --- | ---: | ---: | ---: | ---: |
| initial | 2 | 0 | 3,000,040 | 239,645 |
| 構築済みロイヤルサンプル（selected） | 9 | 1,087 | 3,932,221 | 319,187 |
| all | 60 | 7,684 | 9,374,394 | 794,734 |

サンプルは56種類の入力IDと21種類の関連カードに対して7グループを読む。
これは初回の空キャッシュからの比較であり、既に読み込んだグループの再利用は含めない。
全詳細を読むとindexとの重複分も含むため、全件一括JSONより必ず小さくなる方式ではない。

一覧の値の大きい項目はimage（669,353 bytes / 7,684種類）、product_name（451,920 bytes / 57種類）、
related_cards（371,385 bytes / 3,554種類）。これらは値だけの非圧縮サイズであり、削除してよい項目を示すものではない。
次の削減候補は詳細グループの細分化や、必要な項目を維持した重複表現の圧縮とし、実装前後を同じコマンドで比較する。
この計測追加では配信スキーマ・分割単位・キャッシュ・ルール判定を変更しない。

所有テストは `tools/card_data/measure_catalog_test.py`（ファイル単位のサイズ、関連循環、重複、グループに含まれる全件、
UTF-8/型/欠落、不明ID、入力非変更）と `tools/python_entrypoints_test.py`（モジュール起動、標準出力、終了コード、
既存生成物の検証、不正入力・破損時にもファイルを変更しないこと）。実行は `npm run test:python`。
